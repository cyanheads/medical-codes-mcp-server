# medical-codes-mcp-server — Design

US healthcare code systems as one offline lookup-and-crosswalk server. Decode a code, find the code for a described condition/procedure/drug, validate billability, and crosswalk across systems — keyless, offline, no rate limit. Backed by a SQLite + FTS5 index built at package-build time from public-domain federal code sets.

## MCP Surface

### Tools

| Name | Description | Key Inputs | Annotations |
|:-----|:------------|:-----------|:------------|
| `medcode_get_code` | Decode one or more codes to their official descriptions across ICD-10-CM, ICD-10-PCS, HCPCS Level II, and RxNorm. Auto-detects the system from each code's shape, or accepts an explicit `system` to disambiguate. The 80% entry point — resolve a code seen in a claim, EHR field, or another health server's output into its meaning. | `codes` (1–50 codes), `system?` (enum), `includeHierarchy?` | `readOnlyHint`, `idempotentHint`, `openWorldHint:false` |
| `medcode_search_codes` | Find codes whose official descriptions match a described concept, via full-text search over the bundled index. Filter by system, billable status, and chapter. Use when you have a clinical description ("type 2 diabetes with diabetic neuropathy") and need the code, not the other way round. | `query`, `system?`, `billableOnly?`, `chapter?`, `limit?`, `cursor?` | `readOnlyHint`, `idempotentHint`, `openWorldHint:false` |
| `medcode_check_code` | Validate whether a code exists, is current, and is billable in the active release. Cheap orientation / provenance call. | _(none)_ | `readOnlyHint`, `idempotentHint`, `openWorldHint:false` |

## Overview

**What it does.** Indexes four US federal healthcare code systems from disk and exposes lookup, search, validation, crosswalk, and hierarchy-browse over them. Every tool is a local SQLite query; there is **no runtime API, no network call, no API key, no rate limit**.

**What it wraps.** Bulk public-domain file releases, built into a bundled SQLite + FTS5 database at package-build time:

| System | Owner / license | Covers | Update cadence |
|:-------|:----------------|:-------|:---------------|
| ICD-10-CM | CDC/NCHS — US federal public domain | Diagnoses (FY2027: 74,879 billable leaf codes; 98,403 total rows including non-billable headers) | Annual (Oct 1), mid-year addenda (Apr 1) |
| ICD-10-PCS | CMS — US federal public domain | Inpatient procedures (FY2027: 79,256 codes, plus 918 three-character table rows) | Annual (Oct 1), mid-year addenda (Apr 1) |
| HCPCS Level II | CMS — US federal public domain | Supplies, drugs, non-physician services (October 2026: 8,770 codes, 1,322 of them terminated) | Quarterly (Jan 1, Apr 1, Jul 1, Oct 1) Alpha-Numeric files; temporary codes (G, K, Q prefixes) update on a flow basis |
| RxNorm (current normalized set, via RxNav) | NLM — public domain | Normalized drug names: ingredients, brands, clinical/branded drugs and packs, with RXCUIs, NDC links, and ingredient/brand edges (56,085 concepts in the October 2026 snapshot) | Monthly |
| RxClass drug classes (via the RxClass API) — a class layer over the RxNorm concepts, not a code system | US government sources only: VA MED-RT, FDA SPL, Federal Medication Terminologies, VA National Formulary, RxNorm DEA schedules, CDC CVX | 20,723 classes and 87,269 drug–class edges: pharmacologic class, mechanism, physiologic effect, pharmacokinetics, therapeutic category, chemical structure, disease relations (indications and contraindications), VA class, DEA schedule, vaccine code | Per source — each source's RxClass version is recorded and reported |

**Deliberately excluded:** CPT (AMA copyright), SNOMED CT / LOINC (UMLS-license-gated), and the ATC, ATCPROD, SNOMEDCT, and DAILYMED RxClass sources. The server's value is the union of the *freely-redistributable* code sets — bundling a license-gated set would poison the package. See Design Decisions §1.

**Who it's for.** Medical coders and billers; health-IT and claims engineers; clinical-NLP and research teams; and agents decoding a diagnosis/procedure/drug code or mapping a described condition to its code. The fleet has rich health *data* (`openfda`, `clinicaltrials`, `pubmed`, `cdc-health`, `who-gho`) but nothing that resolves or decodes the **codes** those domains run on. This is the reference layer that grounds the rest.

**US scope.** ICD-10-CM/PCS are the US clinical modifications; the name doesn't say "US" but the code sets do. The server description and `medcode_list_systems` output flag this so an agent doesn't mistake it for ICD-10/ICD-11 base or another country's modification.

## User Goals

The surface is designed goal-first. The outcomes an agent (and its human) will accomplish:

1. **Decode** a code to its official description, category, and hierarchy → `medcode_get_code`
2. **Find** the code(s) matching a described diagnosis, procedure, supply, or drug → `medcode_search_codes`
3. **Validate** whether a code exists, is current, and is billable — with a why-not → `medcode_check_code`
4. **Crosswalk** across systems (drug name → RXCUI, NDC ↔ RXCUI, RXCUI → ingredients, RXCUI ↔ drug class) and within a hierarchy (code → parents/children) → `medcode_map_codes`
5. **Browse** a system's hierarchy without a search term → `medcode_browse_hierarchy`
6. **Ground** a code referenced by another health server (`openfda` NDC, `clinicaltrials` condition) into its meaning → `medcode_get_code` + `medcode_map_codes`
7. **Confirm provenance** — which release/fiscal-year is active before acting on a result → `medcode_list_systems`

Goals 1–7 are fully covered by the six tools. A tool-only agent can accomplish everything the server is for.

## Requirements

- **Offline, keyless, deterministic.** No runtime network I/O. Same inputs + same bundled DB → same output. No auth, no rate limit, single-tenant.
- **Bundled corpus.** The SQLite DB ships inside the package and Docker image — the server reads it read-only at startup. No fetch-at-install, no first-run download. (Build-time ingest; see Services + Design Decisions §2.)
- **Code-shape auto-detection.** ICD-10-CM (`A00`–`Z99` letter + 2 digits + optional `.` + up to 4 more alphanumerics), ICD-10-PCS (7-char alphanumeric, no letters `I`/`O`), HCPCS Level II (1 letter `A`–`V` + 4 digits), RXCUI (pure integer) have distinct shapes. `medcode_get_code`/`medcode_check_code`/`medcode_map_codes` route by pattern; an explicit `system` overrides when a value is ambiguous (e.g. a short string that could be a partial ICD-10-CM category or an HCPCS code). The patterns describe *complete* codes, so they narrow rather than decide: DB membership is the arbiter, and when no shaped candidate is a member the search widens to every bundled system. That keeps the header rows the index materializes — the HCPCS letter buckets (`J`) and the 3-character ICD-10-PCS table rows (`001`, `00B`) — decodable without an explicit `system`, since browse and search both hand them back. The 61 PCS table rows that are also ICD-10-CM categories (`B00`) are the one case where the shape pass picks between two real members: only the ICD-10-CM pattern admits a 3-character letter+2-digit value, so they resolve there and reaching the PCS row needs an explicit `system`. Widening them instead would turn 61 working lookups into `ambiguous_system`, so the resolution is left exactly as it is and the excluded member is *disclosed* on the success path — see §9. The ICD-10-CM display form is the other signal that decides: a value written with its dot (`A01.00`) whose dot-blind lookup comes back ambiguous with ICD-10-CM among the holders resolves to ICD-10-CM, the only system whose codes carry a dot, and the other holder is disclosed the same way. It applies only to an ambiguous outcome, so the undotted `A0100` stays `ambiguous_system` and no value that resolved to one system, or to none, changes.
- **Billable/validity is real signal.** ICD-10-CM carries a billable flag (order-file position 15: `1` = billable leaf, `0` = non-billable header). `medcode_check_code` surfaces "valid category but not billable — needs a more specific child" rather than a bare hit. This is the caller-DX detail a smaller model needs to avoid submitting an unbillable code.
- **Release transparency.** Each system's release identifier (e.g. "ICD-10-CM FY2027", "HCPCS 2026 October", or "RxNorm (current normalized set)" dated by its RxNav snapshot), effective date range, and code count are queryable via `medcode_list_systems` and stamped into a build-metadata row.
- **Licensing posture.** Only freely-redistributable public-domain sets are bundled. RxNorm is the public-domain normalized vocabulary, fetched at build time over the keyless RxNav API — never the full monthly RRF release, which would drag in UMLS-licensed source vocabularies and break redistribution. See Design Decisions §1.

## Services

One service. The server *is* the source of truth (server-as-service pattern) — there is no upstream to retry, no resilience/backoff layer, no API-efficiency table. The design questions are storage-shaped, not network-shaped.

| Service | Wraps | Used By |
|:--------|:------|:--------|
| `code-index` | The bundled SQLite + FTS5 database (read-only handle, opened once in `setup()`) | all six tools |

**`code-index-service`** responsibilities:
- Open the bundled DB read-only at startup (`bun:sqlite`, `readonly: true`), assert the build-metadata table exists and is non-empty (fail-fast on a missing/empty DB — a broken bundle should crash loudly, not serve empty results).
- Expose typed query methods the tools compose: `getByCode(code, system?)`, `searchFts(query, filters)`, `checkCode(code, system?)`, `mapCode(from, direction, system?, page?, classType?)`, `browse(system, node?, page)`, `listSystems()`, `classLayer()`, plus the `hasRxNorm()` / `hasClassLayer()` gates behind `direction_unavailable`.
- Own code-shape detection (`detectSystem(code): SystemId | null`) and the FTS5 query translation (sanitize user text → FTS5 `MATCH` expression).
- No `ctx.state` — the corpus is global and read-only, not tenant-scoped. (No per-tenant data exists; `ctx.state` would be the wrong tool.)

**Schema (one DB, a handful of tables):**

- `codes` — `system TEXT, code TEXT, short_desc TEXT, long_desc TEXT, billable INTEGER, header INTEGER, chapter TEXT, parent TEXT, effective TEXT, terminated TEXT`, PK `(system, code)`. The spine. Note: `parent` is meaningful for ICD-10-CM (parent = code with last character stripped) and HCPCS (parent = first letter range); for ICD-10-PCS it is `NULL` — PCS hierarchy is axis-based, not prefix-based, and only its position-1 Section axis is stored (in `pcs_axes`).
- `codes_fts` — FTS5 external-content index over `short_desc, long_desc` (mirrors `codes`), for `medcode_search_codes`.
- `pcs_axes` — `position INTEGER, value TEXT, meaning TEXT` — ICD-10-PCS axis-value lookup table holding the position-1 Section axis only. `medcode_browse_hierarchy` lists it when called for ICD-10-PCS with no `node`; positions 2–7 depend on the preceding axis path and are not stored, so a partial PCS code does not expand. Built from the PCS tabular XML (`icd10pcs_tables_<FY>.xml`, also in the CMS download) rather than the order file.
- `rxnorm_rel` — `rxcui TEXT, rel TEXT, target TEXT, target_type TEXT` — RXCUI ↔ ingredient/brand/NDC edges, for `medcode_map_codes` drug crosswalks (built from the RxNav `related.json` cache).
- `ndc_map` — `ndc TEXT, rxcui TEXT` (built from the RxNav `ndcs.json` cache), the NDC ↔ RXCUI index that composes with `openfda`.
- `build_meta` — `system TEXT, release_id TEXT, effective_start TEXT, effective_end TEXT, code_count INTEGER, source_url TEXT, built_at TEXT` — one row per system, the provenance `medcode_list_systems` returns. For RxNorm, which has no release label, `built_at` is the RxNav snapshot date: the time `fetch-rxnav.ts` completed its cache, recorded in `.sources/rxnav/meta.json` and read by the build, so a rebuild from the same cache reports the same date. The other systems carry the build time.
- `rxclass_class` — `class_type TEXT, class_id TEXT, class_name TEXT`, PK `(class_type, class_id)` — every class node of the bundled class types, hierarchy nodes with no direct member included. A class ID is unique within its type only (a few MeSH IDs are both `CHEM` and `DISEASE`).
- `rxclass_edge` — `rxcui TEXT, class_type TEXT, class_id TEXT, source TEXT, relation TEXT`, PK over all five — one row per bundled RXCUI × class × asserting source × relation, exactly as RxClass attaches it (mostly at `IN`/`PIN`/`MIN`; DEA schedules only at the product, VA classes almost only there — 46 of the 19,855 VA edges sit on ingredient concepts). Nothing inherited is stored: `rxcui_to_classes` reaches a product's ingredient classes through `rxnorm_rel has_ingredient` at query time. `relation` is lowercased to RxClass's own `relas` vocabulary.
- `rxclass_source` — `source TEXT, version TEXT, class_count INTEGER, edge_count INTEGER, fetched_at TEXT` — per bundled source, the provenance `medcode_list_systems` returns under `classLayer`. `version` is null where RxClass publishes none (CDC); `fetched_at` is the time `fetch-rxclass.ts` completed its cache, recorded in `.sources/rxclass/meta.json`, never the build time. The class layer is not a system, so it has no `build_meta` row and no `SYSTEM_IDS` entry. An index built before the layer has none of these three tables, and one built from sources with no RxClass cache has them empty; neither carries the layer, so the class directions report `direction_unavailable` on both and `classLayer` is null.

**Ingest (build-time, not runtime).** A `scripts/build-index.ts` (run on the federal update cadence, output committed/baked into the image — *not* executed at server startup) that, per system:
1. Reads the canonical release files, extracted beforehand from their `.gov` sources (URLs in Config / Design Decisions §2) — the script never downloads.
2. Parses the format: ICD-10-CM/PCS order files = fixed-width slice by documented column positions; HCPCS `ANWEB.txt` = fixed-width (up to 320 chars/row, right-trimmed in some quarterly files — not delimited, despite the "columns" label in CMS docs); RxNorm = the RxNav JSON cache written by `scripts/ingest/fetch-rxnav.ts`; RxClass = the JSON cache written by `scripts/ingest/fetch-rxclass.ts`.
3. Normalizes into the `codes`/`rxnorm_rel`/`ndc_map` rows, derives `parent`/`chapter`/`header` from code structure (CM/HCPCS only; PCS `parent` stays NULL and hierarchy data populates `pcs_axes` from the tabular XML), writes `build_meta`; then keys the RxClass edges on the bundled RxNorm concepts, dropping the excluded sources and any edge to an RXCUI outside the bundle, and writes `rxclass_class` / `rxclass_edge` / `rxclass_source`.
4. Emits the single `.db` file the package ships.

This is the `MirrorService`'s ingester role done **at build time** rather than at runtime — see Design Decisions §3 for why a build-time bake beats the runtime `MirrorService` here.

## Config

Runtime config is nearly empty — the server reads a bundled file and serves it. Server-specific env vars live in `src/config/server-config.ts` (separate Zod schema, `parseEnvConfig`).

| Env Var | Required | Description |
|:--------|:---------|:------------|
| `MEDCODE_DB_PATH` | no | Absolute path override for the bundled SQLite DB. Defaults to the packaged `data/medical-codes.db` resolved relative to the build output. Override only for a custom-built or externally-mounted index. |
| `MEDCODE_MAX_RESULTS` | no | Default page size when a call sends no `limit` — `medcode_search_codes`, `medcode_browse_hierarchy`, and the paginated `medcode_map_codes` directions — and the number of children `medcode_get_code` attaches with `includeHierarchy` (default 50, hard ceiling 200). Bounds context budget. |

Build-time-only inputs (source URLs, release year/quarter/month) are **script arguments / constants in `scripts/build-index.ts`**, not runtime env vars — the server never downloads anything, so they have no place in `server-config.ts`.

## Implementation Order

Each step is independently testable.

1. **Config + server setup** — `server-config.ts` (DB path, max results), `index.ts` `createApp({ name: 'medical-codes-mcp-server', title: 'medical-codes-mcp-server', ... })`, empty definition barrels.
2. **Build script + a seed DB** — `scripts/build-index.ts` for ICD-10-CM first (smallest blast radius, exercises fixed-width parse + billable flag + FTS), produce a checked-in `data/medical-codes.db`. Unit-test the parser against a fixture slice of the order file.
3. **`code-index-service`** — open the seed DB read-only, implement `getByCode` / `searchFts` / `listSystems` / `detectSystem`. Test against the seed DB.
4. **Read-only tools, in goal order:** `medcode_list_systems` → `medcode_get_code` → `medcode_search_codes` → `medcode_check_code` → `medcode_browse_hierarchy`. Each ships with a sparse-payload test (a code with no short desc, a header row, an empty-result search).
5. **Extend the build to ICD-10-PCS + HCPCS** — add the two parsers, re-bake, verify counts in `build_meta` match the published totals (79,256 PCS codes in FY2027, per its `order_addenda` summary; HCPCS active-code count varies by release — verify against CMS quarterly release notes rather than a fixed expected number).
6. **RxNorm (phase 2)** — add the RxNorm parse (`codes` + `rxnorm_rel` + `ndc_map`, from the RxNav cache — see the 0.2.0 update under Design Decisions §4), then `medcode_map_codes`. This is the only system with relational crosswalk complexity; landing it last keeps v1 unambiguously public-domain (see Design Decisions §4).

(No "write tools / resources / prompts" steps — the server has none.)

## Domain Mapping

Four systems (nouns) × the operations each supports. Operations are raw material; not all become distinct tools — most fold into the six workflow/lookup tools via the `system` parameter.

| System (noun) | Operations the index supports | Served by |
|:--------------|:------------------------------|:----------|
| ICD-10-CM | get-by-code, search-by-desc, check-billable, browse chapter→category→code, code→parent/children | get / search / check / browse / map |
| ICD-10-PCS | get-by-code, search-by-desc, validate (7-char completeness), browse the top-level Section axis (not a prefix hierarchy — each character is an axis: section/body-system/operation/body-part/approach/device/qualifier; positions 2–7 are not enumerable) | get / search / check / browse |
| HCPCS Level II | get-by-code, search-by-desc, check-current (term date), browse by range (A–V) | get / search / check / browse |
| RxNorm | get-by-RXCUI, search-by-drug-name, name→RXCUI, NDC↔RXCUI, RXCUI→ingredients/brands, RXCUI↔RxClass class | get / search / map |

The `system` enum on each tool is what collapses 4 nouns × ~5 operations into 6 tools instead of ~20 — one `medcode_get_code` decodes all four systems, not `medcode_get_icd10cm` + `medcode_get_pcs` + … (Design Decisions §5).

## Design Decisions

### 1. Licensing is the whole architecture — the exclusions are load-bearing

The server's value proposition is *the union of the freely-redistributable US code sets, bundled offline*. That only works if every bundled set is genuinely redistributable:

- **ICD-10-CM** (CDC/NCHS), **ICD-10-PCS** (CMS), **HCPCS Level II** (CMS) — US federal works, public domain, no anti-redistribution or anti-AI clause. Clean to bundle.
- **RxNorm normalized vocabulary** (NLM) — the public-domain SAB=RXNORM layer (normalized names, RXCUIs, NDC links, ingredient/brand edges), fetched at build time over the keyless RxNav API, which serves only that layer. The original plan used the RRF *Prescribable Content* subset; NLM has since moved the RRF bulk files behind UMLS login (see the 0.2.0 update under §4). **This is the only nuance in the whole server**, and it's a sourcing detail, not a blocker.
- **CPT** (AMA copyright), **SNOMED CT / LOINC** (UMLS-license-gated) — *excluded*. Bundling any of them would require a license we can't redistribute under — the same trap that would sink a "bundle BoardGameGeek's data" server. They are out, permanently, by design.
- **RxClass drug classes** — per source, since RxClass aggregates sources with different owners. Bundled, all US government works: `MEDRT` (VA MED-RT), `FDASPL` (FDA established pharmacologic classes from structured product labels), `FMTSME` (Federal Medication Terminologies therapeutic categories), `VA` (VA National Formulary classes), `RXNORM` (DEA controlled-substance schedules as RxNorm records them — covered by the RxNorm public-domain terms), and `CDC` (CVX vaccine codes). Excluded: `ATC` and `ATCPROD`, whose WHO terms state "Copying and distribution for commercial purposes is not allowed" — incompatible with an Apache-2.0 package; `SNOMEDCT`, under the SNOMED CT Affiliate license; and `DAILYMED`, which is redistributable but repeats FDASPL (8,696 of its 8,710 edges) and publishes no version to record. The MeSH IDs that name the `CHEM` and `DISEASE` classes are NLM-provided identifiers, not SNOMED content. The build filters by source, so a new RxClass source is never bundled without being added to `RXCLASS_SOURCES` deliberately.

The hard build-time rule: *never* pull the full monthly RxNorm release. It bundles UMLS-licensed source vocabularies; shipping it would silently convert a clean public-domain package into a license-violating one. The build acquires RxNorm only through RxNav (`scripts/ingest/fetch-rxnav.ts`), and the fetcher's header records why, so a future maintainer doesn't "upgrade" to the full release.

### 2. Data sources — exact files, formats, and parse points

Verified against primary `.gov` sources (October 2026). ICD-10-CM, ICD-10-PCS, and HCPCS are static bulk downloads; RxNorm and RxClass are fetched over the keyless RxNav APIs at build time. None needs a key, and none is called at runtime:

| System | Canonical source | File | Format / parse |
|:-------|:-----------------|:-----|:---------------|
| ICD-10-CM | CDC NCHS FTP: `ftp.cdc.gov/pub/Health_Statistics/NCHS/Publications/ICD10CM/<FY>/` | `icd10cm-code-descriptions-<FY>.zip` → `icd10cm-code-descriptions-<FY>/icd10cm-order-<FY>.txt` (dashes, not underscores; extract it flat, since the build's file probe does not recurse) | Fixed-width, variable-length lines (observed 81–305 chars). **Pos 1–5** order#, **pos 7–13** code (no dot, right-padded with spaces to 7 chars), **pos 15** billable flag (`1`/`0`), **pos 17–76** short desc (space-padded to 60 chars), **pos 78+** long desc. The pos-15 flag is the billable signal `medcode_check_code` depends on. FY2027 file: 98,403 lines — 74,879 billable leaf codes + 23,524 non-billable header/category rows. An `icd10cm-order-addenda-<FY>.txt` change list ships in the same ZIP, but the published order file already incorporates it (see the note below the table), so the build bakes the order file directly. |
| ICD-10-PCS | CMS ICD-10 page (cms.gov — blocks programmatic access; use direct file URL) | `<FY>-icd-10-pcs-order-file-long-abbreviated-titles.zip` → `icd10pcs_order_<FY>.txt` (+ `<FY>-icd-10-pcs-code-tables-index.zip` → `icd10pcs_tables_<FY>.xml` for `pcs_axes`) | Fixed-width. Same column layout as ICD-10-CM order files: **pos 1–5** order#, **pos 7–13** code (7-char alphanumeric, no spaces), **pos 15** valid flag, **pos 17–76** short desc, **pos 78+** long desc. Every complete 7-char PCS code is billable — the valid flag marks completeness; the 3-character table rows carry `0` and are stored non-billable, never as headers. FY2027 file: 80,174 lines — 79,256 valid codes + 918 table rows. Hierarchy is axis-based (7 characters × axis meanings), not parent-code-prefix based. |
| HCPCS Level II | CMS HCPCS quarterly-update page — one Alpha-Numeric file per quarter (January, April, July, October) | `HCPC<yr>_<MON>_ANWEB_<MMDDYYYY>.txt` (e.g. `HCPC2026_OCT_ANWEB_09232026.txt` inside `october-2026-alpha-numeric-hcpcs-file.zip`). The build reads the release from this name — `HCPCS 2026 October`, effective 2026-10-01 through the year end — so keep it as published. | **Fixed-width** (up to 320 chars/row — not delimited; the January 2026 file pads every row to 320, the October 2026 file right-trims each row at its last non-blank column, so the parser reads every field by slice). Column positions verified against the record-layout doc shipped in the ZIP (`HCPC<yr>_recordlayout.txt`): **pos 1–5** HCPC code (5 chars; modifier rows instead carry a 2-char value at pos 4–5 with pos 1–3 blank — filtered out), **pos 6–10** SEQNUM, **pos 11** RECID (`3` = primary row, `4` = long-description continuation), **pos 12–91** LONG_DESCRIPTION (80 chars), **pos 92–119** SHORT_DESCRIPTION (28 chars), **pos 269–276** Code Added Date (effective), **pos 277–284** Action Effective Date (NOT termination — a past date here is normal for active codes), **pos 285–292** Termination Date (YYYYMMDD, blank = active). A code's long description spans the primary row plus continuation rows (same code, successive SEQNUMs) and must be concatenated; terminated codes remain in the file (a code stays active through its termination date, the last date it may be used). October 2026 file: 16,899 rows → 8,770 distinct codes (7,448 active, 1,322 terminated). |
| RxNorm | NLM RxNav REST API (`rxnav.nlm.nih.gov/REST/`), keyless — fetched at build time by `scripts/ingest/fetch-rxnav.ts` into `.sources/rxnav/`, never at runtime | `allconcepts.json?tty=…` (the concept set), then per drug product `ndcs.json` and `related.json?tty=IN+PIN+MIN+BN` | JSON. `parseRxNav()` turns the cache into `codes(RXNORM)` rows, `ndc_map` (11-digit NDC ↔ RXCUI), and `rxnorm_rel` (ingredient/brand edges). |
| RxClass | NLM RxClass REST API (`rxnav.nlm.nih.gov/REST/rxclass/`), keyless — fetched at build time by `scripts/ingest/fetch-rxclass.ts` into `.sources/rxclass/`, after the RxNav cache it keys on, never at runtime | `version/<SRC>.json` per bundled source (the documented `version/relaSource.json?relaSource=` form returns 404), `allClasses.json?classTypes=<T>` per class type, then `class/byRxcui.json?rxcui=<id>` per bundled `IN`/`MIN` — RxClass answers an ingredient with its own edges and those of its precise ingredients, multi-ingredients, and products | JSON. `parseRxClass()` keeps the bundled sources and bundled RXCUIs and lowercases each rela (`byRxcui` spells VA's `has_VAClass`; RxClass's `relas` vocabulary spells `has_vaclass`), producing `rxclass_class`, `rxclass_edge`, and `rxclass_source`. |

ICD-10's mid-year addenda (Apr 1) means the "active" FY file can change twice a year. `build_meta.release_id` names the fiscal-year release only (`ICD-10-CM FY2027`), not which mid-year revision was baked, and both ICD-10 systems carry the fiscal-year bounds (2026-10-01 – 2027-09-30) even though CMS scopes the October ICD-10-PCS files to discharges through 2027-03-31. The FY2027 ICD-10-PCS order file (last modified 2026-06-05) lacks XW0U3CC and XW0U4CC, which the CMS FY2027 errata (2026-08-21) adds; the build reads the order file as published, so both answer `unknown_code` until CMS publishes a file that carries them. Verified for FY2026: the published order file **already incorporates** the April addenda (all 630 addenda "Add" codes are present in the base file, none net-new), so the build bakes the base file directly and does **not** apply the separate `*-order-addenda-*.txt` change list — that file uses a different layout (Add/Delete/Revise actions, code at a shifted column) and trailing summary lines, and re-parsing it with the order-file parser yields colliding garbage rows. If a future release ships an order file that predates its addenda, an addenda-specific parser would be needed.

### 3. Ingest strategy — build-time bake, not the runtime MirrorService

The corpus is **tiny and changes on a slow, scheduled cadence**: on the order of ~243k code rows total (ICD-10-CM ~98k rows / ~75k billable, ICD-10-PCS ~80k, HCPCS ~9k rows, RxNorm ~56k concepts, plus the RxNorm edge and NDC tables; exact counts land in `build_meta` at build time), updated annually (ICD-10), quarterly (HCPCS), monthly (RxNorm) — never intra-day, never per-request. The design skill's backend-by-corpus-size guidance maps three ways, and this corpus sits at the small end:

| Option | Fit here |
|:-------|:---------|
| In-memory index (≲ tens of thousands of rows) | Borderline on row count, but loses FTS5 and forces a parse on every cold start. |
| **Build-time SQLite + FTS5, baked into the image** | **Chosen.** Corpus is bounded and slow-changing; bake it once, ship the `.db`, open read-only. Zero cold-start parse, FTS5 search for free, fully offline, deterministic. |
| `MirrorService` (runtime sync, 10⁴–10⁷) | Designed for a *live upstream queried more than it changes*, with a runtime `sync` generator + scheduler. Overkill here: there is no live API to mirror at runtime, and the federal cadence is far slower than any refresh loop. Its machinery (cursor/checkpoint, runtime scheduler, init-vs-refresh) solves problems this corpus doesn't have. |
| External store (≳ 10⁸) | Irrelevant at ~243k rows. |

So the architecture borrows the `MirrorService` *shape* — SQLite + FTS5, an ingester per source — but runs the ingester **at build time** and ships the result. The federal update cadence is a CI/rebuild trigger, not a runtime concern. `mirror: "T1 — entire code set built into SQLite+FTS5 at build time"` in the fleet entry already names this; this design pins the mechanics.

**Bundle vs. fetch-at-install:** bundle. The full DB is on the order of tens of MB — small enough to ship in the npm tarball and Docker image, and bundling preserves the offline/keyless/deterministic guarantee. A fetch-at-install step would add a network dependency and a failure mode the whole design exists to avoid.

### 4. Clean v1, then RxNorm (phase 2)

ICD-10-CM/PCS + HCPCS are unambiguously public domain and parse from fixed-width/columnar text → they ship as a clean v1 with zero licensing nuance and no relational crosswalk. RxNorm adds the only cross-system relational tables (`rxnorm_rel`, `ndc_map`). Landing it as a second phase kept the first release simple and unambiguous. The server identity is "US medical codes" either way — this was a sequencing call, not a scope change. `medcode_map_codes`'s drug directions shipped inert (`direction_unavailable`) in v1, with the hierarchy directions live.

**Update (0.2.0 — RxNorm landed):** the acquisition pivoted from the RRF files to the **keyless RxNav REST API** (`scripts/ingest/fetch-rxnav.ts`), because NLM moved the RxNorm RRF bulk downloads — including the prescribable subset — behind UMLS/UTS authentication, which an offline keyless package can't depend on. RxNav serves the public-domain RxNorm *normalized* vocabulary (never the UMLS-licensed source vocabularies), so the bundled scope is the **current normalized drug set** (ingredients, brands, clinical/branded drugs, packs) with their NDC + ingredient/brand edges — a superset of the prescribable subset, and still fully redistributable. The drug directions and first-class NDC → drug decode in `medcode_get_code` are now live.

### 5. The `system` enum collapses the surface; auto-detection keeps it ergonomic

Four code systems could have produced a per-system tool explosion (`medcode_get_icd10cm`, `medcode_search_hcpcs`, …) — ~20 tools mirroring nouns. Instead, one tool per *user action*, with a `system` discriminator. `medcode_get_code` decodes any of the four; the handler routes by code shape and only needs `system` when a value is genuinely ambiguous. This is the goal-first surface the skill prescribes: the agent says "decode this code," not "which of four lookup tools matches this code's system." Output always echoes the resolved `system` so the agent knows which system answered — provenance the server can know and the agent can't infer reliably from the code alone.

### 6. No resources — tool-only by design

Every datum is reachable through the tool surface, and the primary clients (Claude Code, Cursor, chat UIs) are tool-only. A `medcode://icd10cm/{code}` resource would duplicate `medcode_get_code` with no added reach — and data locked behind a resource is invisible to tool-only clients, the exact trap the skill flags. Stable-URI injectable context isn't a meaningful win for a code-lookup server where the agent already drives every lookup by tool call. Skipped.

### 7. No prompts

No recurring multi-step interaction pattern that a reusable message template would structure. Lookups and crosswalks are direct tool calls; there's no "analysis framework" or "report template" shape here. The "clinical-concept resolver" moonshot (free text → candidate ICD-10-CM + RXCUI + procedure codes in one call) *could* one day be a workflow **tool** (not a prompt) — deferred, noted, out of v1 scope.

### 8. No DataCanvas

The skill gates DataCanvas on *analytical shape* — would an agent run SQL (aggregate/group/join) over the result? No. This is a lookup/crosswalk/discovery surface returning a handful of codes per call, the categorical-metadata case the skill explicitly says does *not* qualify regardless of corpus size. Results return inline; FTS5 over the bundled DB is the search backend. A `dataframe_query` tool would be dead surface here.

### 9. Output design — built for the agent's next move

- `medcode_get_code` returns, per code: resolved `system`, `code` (display form with dots re-inserted), `description` (long), `shortDescription`, `billable`, `header`, `chapter`, and (when `includeHierarchy`) `parent` + immediate `children`. The agent can chain straight into a `medcode_map_codes` parents/children walk (the drug directions take no `system` but `RXNORM`) or surface a billability warning without a second call.
- A field the system's release does not carry is `null`, never the placeholder the `codes` row stores for it: RxNorm has no billing concept (`billable: null`, rendered `billable: n/a`) and publishes a single name (`shortDescription: null`), and its term type (`IN`, `SCD`, `SBD`, …) is carried in `chapter`, where the search `chapter` filter reads it. One per-system record (`SYSTEM_TRAITS` in `types.ts`) drives both, so the stored placeholders stay and the index is not rebuilt. The same record keeps text matching off the placeholder: `medcode_search_codes` and the `name_to_rxcui` crosswalk read only `long_desc` for a system without a short description, at query time, so a query equal to or inside a term type (`SBD`, `in`) never returns every concept of that type.
- `medcode_check_code` returns a discriminated status (`valid_billable` | `valid_not_billable` | `valid_header` | `valid` | `terminated` | `unknown`) plus a `whyNot` string for the non-billable/terminated cases — the recovery instruction a coder acts on. A HCPCS termination date is the last date CMS allows the code on a claim (the record layout's "last date for which a procedure or modifier code may be used"), and the service compares it with the UTC date of the call, not the build: the index can predate a termination it carries, since a quarterly file lists terminations ahead of their date, and the stored `billable` flag is only the build's reading of that rule on the build date. So a code is `terminated` (and `billable: false` on every tool, `billableOnly` search included) from the day after its termination date, and until then it checks `valid_billable` with the date in `whyNot`. The date carries no zone, and UTC keeps the verdict independent of the server's `TZ`; a US caller sees the code turn `terminated` up to ten hours before its own last valid day ends, which errs toward withholding a code rather than passing one that is no longer valid. `valid` is a current code in a system with no billing concept (RxNorm), with `billable: null` and no `whyNot`. An `unknown` value that is a National Drug Code says so and recovers to `medcode_get_code` / `medcode_map_codes` `ndc_to_rxcui` — NDC is a package identifier the server decodes, not a code `check_code` has a verdict for.
- `medcode_search_codes` discloses truncation: `ctx.enrich.truncated({ shown, cap })` when the result hits the cap, and echoes the parsed query + active filters via `ctx.enrich` so both client surfaces see what was searched. Empty results return an explicit notice (try broader terms / different system), not a bare empty array — or, for `billableOnly` on RxNorm, a notice naming that filter as the cause.
- `medcode_map_codes` always returns `source` provenance (which system/edge answered) so a chained call (e.g. into `openfda` with the resolved NDC) carries the right identifier.
- The class directions put the RxClass layer on that same surface rather than a separate tool: both lookups are identifier crosswalks with `source` provenance, and `classType` follows the per-direction field rule of `field_not_applicable`. A class hit carries `classType`, `source` (the RxClass source asserting it), and `relation` — one hit per class × source × relation — and `format()` renders all three, spelling a `ci_` relation out as a contraindication so a text-only reader never takes it for an indication. `rxcui_to_classes` reaches a drug product's ingredient classes through `has_ingredient` and names the ingredient in `via`; the product's own edge wins, then an `IN` over its `PIN`, then the lowest RXCUI, and nothing is inherited downward. RxClass records DEA schedules (and all but a handful of VA classes) on drug products, so an ingredient's empty `SCHEDULE` or `VA` result carries a notice saying where those classes live — without it, "oxycodone has no SCHEDULE class" reads as "oxycodone is unscheduled". Inheriting them downward instead would be wrong: an ingredient's products can carry different schedules (codeine's single-ingredient and combination products differ). `class_to_rxcuis` returns direct members with their RxNorm name and term type, and reads a one-digit CVX code as its zero-padded class ID (`3` → `03`). Both paginate: one RXCUI reaches 178 classes and one class 3,177 edges. `medcode_list_systems` reports the layer under `classLayer`, apart from `systems`, because it is not a code system the other tools' `system` input accepts.
- Multi-code `medcode_get_code` is array-in / partial-success-out: `found[]` + `notFound[]` (with per-code reason), since one bad code in a batch shouldn't fail the others.
- A code string that resolves in one system while existing in another carries `alsoInSystems` on the successful result of `medcode_get_code` (per `found[]` entry), `medcode_check_code`, and `medcode_map_codes` (hierarchy directions) — the 61 ICD-10-CM/ICD-10-PCS collisions above. It is a disclosure on an otherwise unchanged answer, not a second verdict: the agent reads which other system holds the same string and re-calls with `system` if it meant that one. Structured because a batch decode needs the attribution per code, and rendered in `format()` because a `content[]`-only client would otherwise be handed one meaning as if it were the only one.
- Every value a tool did not author (codes, descriptions, RxNorm and RxClass names, release metadata, echoed caller input) reaches `content[]` through `literal()` / `literalAtHeadingEnd()` / `tableRow()` in `_render.ts`, so a CommonMark parse reads it back exactly as `structuredContent` carries it, while tool-written Markdown (headings, bold labels, bullets, table syntax) still renders; a source URL renders as a link through the framework's `markdownLink()`. Notices are escaped whole by each tool's `enrichmentTrailer.render`, so `structuredContent.notice` carries the echoed input as written and only `content[]` gets the escapes. Error messages, recovery hints, and notices are plain text, escaped on the way into `content[]` (error text by the framework, notices by that trailer), so they name fields without backticks.

### 10. Typed error contracts (per tool, inline)

Domain failure modes declared as `errors: [{ reason, code, when, recovery }]` so `ctx.fail` is type-checked and capable clients preview failures via `tools/list`. Baseline codes (`InternalError`, `ValidationError`, …) bubble without declaration.

| Tool | reason | code | when | recovery (agent's next move) |
|:-----|:-------|:-----|:-----|:-----------------------------|
| `medcode_get_code` | `ambiguous_system` | `InvalidParams` | every requested code is present in more than one bundled system and no `system` was given | Re-call with an explicit system to disambiguate. `data.candidateSystems` is the union of the codes' systems in canonical order; one `system` applies to every code in the batch, so a single re-call resolves it. |
| `medcode_get_code` | `no_codes_found` | `NotFound` | none of the requested codes resolved — in any bundled system, or in the explicit `system` when one is given — and at least one failed for a reason other than ambiguity | Verify code formatting, or call `medcode_search_codes` with a description to find the right code. Under an explicit `system`, the message names that system and any other bundled system holding a requested code. It also names each code present in more than one bundled system with those systems, any bare-integer inputs as possible CPT / HCPCS Level I codes, which are out of scope, any well-formed NDC no bundled drug maps to (hyphenated, or bare 10/11 digits, which are never worded as CPT), and any NDC an explicit `system` kept from the NDC decode; the recovery stays, since a batch can fail for mixed causes. |
| `medcode_check_code` | `unknown_code` | `NotFound` | the code does not exist in the named system, or with no `system` in any bundled system | Check the code, or search by description with `medcode_search_codes`. For a value that is an NDC — decoded, or well-formed with no bundled drug mapping to it, bare 10/11 digits included — the message says so and the thrown hint instead names `medcode_get_code` and `medcode_map_codes` `ndc_to_rxcui`. Under an explicit `system`, the message names the other bundled system that holds the code, and the CPT / HCPCS Level I out-of-scope sentence fires only for a bare integer no bundled system holds. With no `system`, the message names every system the value's shape fits (a dotted ICD-10-CM form, ICD-10-CM alone), and a bare integer also gets the out-of-scope sentence. |
| `medcode_check_code` | `ambiguous_system` | `InvalidParams` | the code is present in more than one bundled system and no `system` was given | Re-call with an explicit system to disambiguate. |
| `medcode_map_codes` | `field_not_applicable` | `InvalidParams` | a `system`, `classType`, `limit`, or `cursor` the direction does not use — checked after `direction_unavailable` (re-calling without the field would only reach that error) and before the cursor is decoded or any lookup runs | Drop the named fields and re-call: `system` steers only parents/children (the drug and class directions accept only `RXNORM`, a no-op); `classType` applies only to rxcui_to_classes and class_to_rxcuis; `limit`/`cursor` apply only to children, name_to_rxcui, rxcui_to_ndc, rxcui_to_classes, and class_to_rxcuis. A blank `classType` is an argument rejection like any value outside the enum; only a blank `cursor` counts as omitted. |
| `medcode_map_codes` | `no_mapping` | `NotFound` | the source value did not resolve to a bundled code, drug, or class the direction reads (the `rxcui_to_*` directions read RxNorm concepts only) | Check the code, or decode it with `medcode_get_code` first. A resolvable source with no edge in the direction — or a `cursor` past the last page — is an empty result with a notice, not this error. These misses throw their own hint instead: a code-system name in `from` (`ICD10CM`, `HCPCS Level II`, …) is told where the code and the system go on `parents`/`children`, and on a drug direction the one input that direction takes (a drug name, an NDC, or an RXCUI with the two directions that produce one); a `parents`/`children` source an explicit `system` missed names every other bundled system holding it and recovers to a re-call with that `system`, as `medcode_check_code` and `medcode_get_code` name it; an `ndc_to_rxcui` miss names the accepted FDA segment configurations for a malformed spelling, or says no bundled drug maps to a well-formed NDC, and recovers to the package label or `name_to_rxcui` rather than to `medcode_get_code`; on `parents`/`children`/`rxcui_to_*`, an NDC that `medcode_get_code` would decode is named as an NDC and sent to `ndc_to_rxcui`, a well-formed NDC no bundled drug maps to (hyphenated, or bare 10/11 digits) gets the `ndc_to_rxcui` miss wording and recovery, and any other bare integer no bundled system holds is named as a possible CPT / HCPCS Level I code and sent to `medcode_search_codes`. On `rxcui_to_*`, a source another bundled system holds (`E11.9`, or a digits-only ICD-10-PCS code) is named as that system's code — every holder, for a string two systems hold — with the note that the direction reads RxNorm concepts only, and recovers to `medcode_get_code` with each holder's `system` (a string two systems hold can be ambiguous without one), or a `parents`/`children` walk with that `system` for a holder that has a prefix hierarchy — never ICD-10-PCS, so an ICD-10-PCS-only holder gets the decode step alone. On `rxcui_to_classes` a class ID is named as one and sent to `class_to_rxcuis`, ahead of the bare-integer test (CVX class IDs are bare integers). A `class_to_rxcuis` miss is worded for a class ID, never with the CPT sentence: a code-system name, a class type (`EPC`), or a bundled RXCUI sent in its place is named as such, and anything else is an unbundled class ID, recovered to the class IDs `rxcui_to_classes` returns and a note that ATC, SNOMED CT, and DailyMed classes are not bundled. |
| `medcode_map_codes` | `ambiguous_system` | `InvalidParams` | the source code is present in more than one system and no `system` was given | Re-call with an explicit system to disambiguate. |
| `medcode_map_codes` | `direction_unavailable` | `InvalidParams` | a drug-crosswalk direction requested but the build carries no RxNorm tables, or a class direction requested but it carries no RxClass class layer (an index built before the layer, or from sources with no RxClass cache, whose class tables are empty) | Use a hierarchy direction (parents/children), or rebuild the index with RxNorm bundled (the shipped default). The class case throws its own hint: use another direction, or unset `MEDCODE_DB_PATH` to use the shipped index, which carries the layer. |
| `medcode_browse_hierarchy` | `unknown_node` | `NotFound` | the `node` doesn't exist in the system — for ICD-10-PCS, also a node carrying a character outside the axis alphabet (digits plus A-Z without `I`/`O`) or one no bundled code begins with | Omit node to list top-level entries, or verify the node code. |

Validity vs. existence is deliberately split: a *non-billable* or *terminated* code is a successful `medcode_check_code` result (status + `whyNot`), **not** an error — the agent needs the detail, and throwing would hide it. Only a code that doesn't exist at all is `unknown_code`.

`medcode_get_code` is array-in / partial-success-out: an unresolvable or cross-system-ambiguous code lands in `notFound[]` with its own reason (and `candidateSystems` when ambiguous) rather than failing the batch. A typed error fires only when *every* requested code fails, and then it takes the sharpest reason the batch supports: `ambiguous_system`, with the same code and recovery as `medcode_check_code` and `medcode_map_codes`, when every code failed on ambiguity, since one re-call with a `system` from the union resolves the batch; otherwise `no_codes_found`, whose message carries the per-code causes the thrown error would otherwise drop.

`medcode_search_codes` likewise carries no typed error contract: a zero-match query is a successful empty result with a recovery notice (via enrichment), not a `NotFound`. An empty result set is a normal search outcome, and the notice delivers the same recovery guidance without forcing the caller to catch an error.

## Known Limitations

- **US-only.** ICD-10-CM/PCS are US clinical modifications; no ICD-10/ICD-11 base or other national mods. Flagged in the description and `medcode_list_systems`.
- **No CPT / SNOMED CT / LOINC.** Excluded by license (§1) — a crosswalk *into* CPT or SNOMED is out of scope and can't be added without a redistributable source.
- **Release lag.** The bundled DB is as current as its last build. `medcode_list_systems` exposes exactly which release is active so a caller can detect staleness; there is no live-API fallback (by design — the whole server is offline).
- **RxNorm coverage is the current normalized set, not the full release.** Obsolete and retired concepts and the UMLS-licensed source vocabularies in the full release are absent. This is the redistribution tradeoff, surfaced in `medcode_list_systems` (release_id names the set).
- **RxClass: direct edges, no hierarchy, no ATC.** `class_to_rxcuis` returns direct members only, and 13,601 of the 20,723 bundled classes have none — hierarchy nodes whose drugs attach to their subclasses (`N0000193873` "Diuretic"); there is no subclass walk, class-hierarchy browse, or class-name search. ATC/ATCPROD, SNOMED CT, and DailyMed classes are excluded (§1), and drug–drug interactions are not in the layer. An edge to an RXCUI outside the bundled normalized set (a retired concept, a dose-form group) is dropped at build time.
- **One `via` per inherited class.** A product whose ingredients share a class gets one hit for it, naming one ingredient in `via` (an `IN` over its `PIN`, then the lowest RXCUI). The other ingredients that carry the same class are not named: in the shipped index 5,091 products have 22,909 such edges shared by two or more `IN`s. Map each ingredient with `rxcui_to_classes` to see which carry it.
- **ICD-10-PCS hierarchy is axis-based, not prefix-based.** Unlike ICD-10-CM where a shorter code is always the parent of a longer one, PCS codes have no such prefix relationship — each character independently encodes an axis (section, body system, root operation, body part, approach, device, qualifier). `medcode_browse_hierarchy` for PCS lists only the top-level Section axis values; a partial PCS code does not expand to next-position values, because positions 2–7 depend on the preceding axis path. The `parent` field in the schema has no meaningful value for PCS. PCS codes are found through `medcode_search_codes`.

## API Reference

No external API. Backend is a bundled SQLite + FTS5 database opened read-only via `bun:sqlite`. Search uses FTS5 `MATCH`; the service translates sanitized user text into an FTS5 query expression. Pagination/caps via `MEDCODE_MAX_RESULTS` with `ctx.enrich.truncated()` disclosure.
